1. Introduction to Web Services

A Web Service is a standardized software application designed to support interoperable machine-to-machine interaction over a network. It uses open XML/JSON standards and Internet protocols (HTTP/HTTPS) to allow heterogeneous systems (e.g., Java client communicating with a .NET backend) to exchange data seamlessly.

Key Characteristics of Web Services:

  • Platform & Language Independent: Written in any language (Java, C#, Python) running on any OS (Linux, Windows, Unix).
  • Loose Coupling: Client and server components are decoupled; interface changes do not break client implementation.
  • Standardized Protocols: Relies on universally accepted industry standards: XML, SOAP, WSDL, and UDDI.
  • Firewall Friendly: Uses standard HTTP/HTTPS ports (80/443), eliminating custom firewall configuration barriers.

2. Web Service Architecture (Publish-Find-Bind Triangle)

The Web Service Architecture revolves around three core architectural entities and three operations:

The Web Service Triangle:

• Service Provider: Creates the web service and makes it available on the Internet. It defines the service description using WSDL and publishes it to a service registry.

• Service Registry (Broker): A central searchable repository (UDDI) that catalogs service descriptions submitted by service providers.

• Service Requester (Consumer): The client application that wants to invoke the service. It finds the service in the registry, retrieves the WSDL interface, and binds to the provider over SOAP/HTTP.

The Three Core Operations:

  1. Publish: Provider registers the service description in UDDI.
  2. Find: Consumer queries UDDI to locate a specific service based on criteria.
  3. Bind: Consumer invokes the service using contract specifications found in the WSDL file.

3. Core Web Service Protocols: UDDI, SOAP & WSDL

3.1 UDDI (Universal Description, Discovery, and Integration)

UDDI is an XML-based registry standard that acts as the "Yellow Pages" for web businesses and their electronic services.

UDDI organizes information into three categories:

  • White Pages: Basic contact details (business name, address, phone number, website, unique identifier).
  • Yellow Pages: Categorizes services based on standard industrial taxonomy codes (e.g., NAICS, UN/SPSC).
  • Green Pages: Technical specifications and binding details pointing to the WSDL files describing how to interact with the service.

3.2 SOAP (Simple Object Access Protocol)

SOAP is a formal XML-based protocol specification for exchanging structured information in decentralized, distributed environments over application protocols such as HTTP or SMTP.

Structure of a SOAP Message:

<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
    <soap:Header>
        <!-- Optional: Authentication tokens, transactions, routing -->
        <auth:Token xmlns:auth="http://example.com/auth">xyz9876</auth:Token>
    </soap:Header>
    <soap:Body>
        <!-- Mandatory: Actual request or response payload -->
        <m:GetStockPrice xmlns:m="http://example.com/stocks">
            <m:StockTicker>GOOG</m:StockTicker>
        </m:GetStockPrice>
        <!-- Optional: SOAP Fault element for error handling -->
    </soap:Body>
</soap:Envelope>
  • Envelope (Mandatory): Root element identifying the XML document as a SOAP message.
  • Header (Optional): Contains application-specific information such as authentication, encryption, and routing data.
  • Body (Mandatory): Holds the actual call data, parameters, or return response.
  • Fault (Optional): Sub-element inside Body used exclusively to carry error and exception status information.

3.3 WSDL (Web Services Description Language)

WSDL is an XML format for describing network services as a set of endpoints operating on messages containing either document-oriented or RPC-oriented information.

Section Level WSDL Element Function / Purpose
Abstract Definitions
(Independent of platform/wire)		 <types> Defines data types using XML Schema (XSD).
<message> Defines the data parameters for input and output operations.
<portType> Defines callable operations (methods) and related messages (like an Interface).
Concrete Definitions
(Transport & network binding)		 <binding> Specifies communication protocol (e.g., SOAP over HTTP) and message formats.
<service> / <port> Specifies the physical endpoint address (URL) where the service resides.

4. Developing and Deploying Web Services

Building and releasing a web service typically involves two distinct design methodologies:

  • Contract-First (Top-Down): Write the WSDL & XSD first; then auto-generate server skeleton code and client stubs (ensures high cross-platform compatibility).
  • Code-First (Bottom-Up): Write the Java/C# service class and annotate it (e.g., @WebService in JAX-WS); the framework automatically publishes the WSDL at runtime.

Deployment Steps: Compile service classes → Package into archive (.WAR / .EAR) → Deploy to an enterprise application server (Apache Tomcat with Axis2, GlassFish, WildFly) → Verify WSDL endpoint availability in browser.

5. Ajax (Asynchronous JavaScript and XML)

Ajax is a client-side technique introduced to overcome the traditional synchronous "click-wait-reload" web paradigm.

5.1 Improving Web Page Performance using Ajax:

  • Zero Page Flicker: Only small portions of the page are updated dynamically without refreshing the entire layout.
  • Bandwidth Conservation: Eliminates re-downloading identical headers, sidebars, navigation menus, and CSS stylesheets on every interaction.
  • Responsive Desktop-Like User Experience: Instantaneous auto-complete suggestions, live feeds, and background saves.
  • Asynchronous Non-Blocking Execution: The user can continue interacting with the page while the background data transfer takes place.

5.2 Programming in Ajax: The XMLHttpRequest Object

// Pure JavaScript Ajax Request
function loadUserData() {
    var xhr = new XMLHttpRequest();
    
    // Configure request: method, URL, asynchronous (true)
    xhr.open("GET", "/api/users?id=101", true);
    
    // Register state change listener
    xhr.onreadystatechange = function() {
        if (xhr.readyState === 4 && xhr.status === 200) {
            // Parse server response and update DOM
            document.getElementById("profile").innerHTML = xhr.responseText;
        }
    };
    
    // Send request payload to server
    xhr.send();
}
The 5 ReadyStates of XMLHttpRequest:
• 0: UNSENT — Client created, open() not called yet.
• 1: OPENED — open() called.
• 2: HEADERS_RECEIVED — send() called, headers received.
• 3: LOADING — Downloading response body in chunks.
• 4: DONE — Entire data transfer completed successfully.

6. CORBA (Common Object Request Broker Architecture)

Developed by the Object Management Group (OMG), CORBA is an open vendor-independent architecture and infrastructure that computer applications use to work together over networks.

6.1 Key Components of CORBA:

  • ORB (Object Request Broker): The communication middleware that transparently routes method invocations from client to remote server object and returns results.
  • IDL (Interface Definition Language): A strictly typed declarative language used to define remote object interfaces independent of programming languages.
  • IIOP (Internet Inter-ORB Protocol): TCP/IP-based wire protocol enabling different vendor ORBs to interoperate across the network.

6.2 Web Services vs. CORBA (Comparison):

Feature CORBA Web Services (SOAP/REST)
Data Format Binary (CDR - Common Data Representation). High speed, low readability. Text/XML/JSON. Human readable, platform-neutral.
Transport Protocol Custom TCP ports via IIOP. Usually blocked by enterprise firewalls. Standard HTTP/HTTPS (ports 80/443). Universally accessible across firewalls.
Coupling Tightly coupled binary RPC mechanisms. Loosely coupled message exchange.
Complexity Steep learning curve, high vendor dependency. Simpler, open web-based tooling and ubiquitous browser support.
